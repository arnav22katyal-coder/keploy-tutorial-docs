# Testing Go Applications with Keploy: The Zero-Code Guide

Testing Go backend services has historically forced developers to choose between two painful extremes:
1. **Mocking Hell:** Writing verbose interfaces, dependency injection boilerplate, and fragile `gomock` / `testify` stubs for every database or external API call.
2. **Flaky Integration Tests:** Orchestrating live Docker containers, seeding database state, managing race conditions, and enduring slow CI pipelines.

**Keploy introduces a third way:** It records real API calls alongside downstream network I/O (like Redis, SQL databases, and third-party APIs) directly at the transport layer, generating deterministic test cases and wire-level mocks without altering a single line of your Go code.

In this tutorial, you will take a **Go Gin** user authentication service that depends on **Redis** for OTP (One-Time Password) verification, record real traffic with Keploy, inspect the auto-generated YAML specifications, and replay the tests completely offline—**even with Redis turned off!**

---

<h2 id="why-keploy-for-go">Why Keploy for Go Developers?</h2>

Go is renowned for its speed, simplicity, and rock-solid concurrency. But testing stateful web services in Go frequently introduces interface pollution. To test a handler that touches Redis, you often end up creating:

<CodeBlock language="go" filename="Traditional Go Interface (Mock Boilerplate)">
{`// Traditional approach: interface pollution just for mocking
type OTPStore interface {
    SetOTP(ctx context.Context, email, otp string) error
    GetOTP(ctx context.Context, email string) (string, error)
}`}
</CodeBlock>

While clean architecture is valuable, mocking complex database interactions like Redis TTL expirations, transaction pipelines, and socket failures by hand is tedious and disconnected from production reality.

<Callout type="keploy" title="The Keploy Difference: eBPF & Socket Interception">
Keploy does not require you to rewrite your codebase to use mock interfaces. By attaching to network sockets (via eBPF on Linux or a transparent proxy mechanism), Keploy observes the exact binary protocols exchanged between your Go application and downstream dependencies. When tests replay, Keploy serves the exact recorded bytes back to your client library.
</Callout>

### Understanding the Application Logic

The service exposes two primary authentication endpoints in `main.go`:

1. `POST /user/getOTP`: Accepts an email, generates a 6-digit cryptographic OTP, and sets it in Redis with a 5-minute TTL (`SETEX email 300 otp`).
2. `POST /user/verifyOTP`: Accepts an email and OTP, retrieves the stored OTP from Redis (`GET email`), and verifies whether they match.

Here is a snippet of how standard `go-redis` is invoked in `main.go`:

<CodeBlock language="go" filename="main.go (Simplified Excerpt)">
{`// Generate and store OTP in Redis
rdb := redis.NewClient(&redis.Options{
    Addr: "localhost:6379",
})

r.POST("/user/getOTP", func(c *gin.Context) {
    var req struct {
        Email string \`json:"email"\`
    }
    if err := c.BindJSON(&req); err != nil {
        c.JSON(http.StatusBadRequest, gin.H{"error": "invalid payload"})
        return
    }

    otp := generateOTP(6)
    // Downstream Redis call captured by Keploy:
    err := rdb.Set(c.Request.Context(), req.Email, otp, 5*time.Minute).Err()
    if err != nil {
        c.JSON(http.StatusInternalServerError, gin.H{"error": "failed to store OTP"})
        return
    }

    c.JSON(http.StatusOK, gin.H{
        "status": "success",
        "message": "OTP generated and stored successfully",
    })
})`}
</CodeBlock>

<Callout type="info" title="Zero Instrumentation">
Notice that `main.go` uses standard `github.com/gin-gonic/gin` and `github.com/redis/go-redis/v9`. There are **no Keploy SDK imports, no test wrappers, and no code modifications.**
</Callout>

</Step>

<Step

  title="Spin Up Downstream Redis"

During the **Record** phase, Keploy needs a live instance of Redis so your application can perform its normal operations. We can start Redis quickly using Docker:

<CodeBlock language="bash" filename="Terminal">
{`# Start a lightweight Redis container on port 6379
docker run -p 6379:6379 --name redis-server -d redis:alpine

# Verify Redis is accepting connections
docker exec -it redis-server redis-cli ping
# Expected response: PONG`}
</CodeBlock>

<Callout type="tip" title="Why Redis is only needed once">
You will only need this live Redis container running while you record your initial test cases. Once Keploy captures the network responses, **Redis will never be needed again for your test suite!**
</Callout>

</Step>

<Step
  id="step-3-record-traffic"
  number="03"
  title="Record Traffic with Keploy"
  time="2 min"
  badge="Core Command"
>

Now, instead of launching your application with `go run main.go`, wrap it with `keploy record`:

<CodeBlock language="bash" filename="Terminal">
{`# Launch application under Keploy recording mode
sudo -E keploy record -c "go run main.go"`}
</CodeBlock>

<Callout type="keploy" title="What is happening right now?">
1. Keploy initializes its eBPF network hooks and attaches to your Go process.
2. It launches `go run main.go`. The Gin server starts listening on port `8080`.
3. Keploy monitors inbound traffic on port `8080` and outbound socket traffic to `localhost:6379`.
</Callout>

You should see Keploy terminal logs indicating that the interceptor is active:

<CodeBlock language="bash" filename="Terminal Output">

### What Keploy Did in the Background

As soon as both requests executed:
- **Request 1:** Gin handled `POST /user/getOTP` and executed Redis `SETEX devrel@keploy.io 300 849201`. Keploy recorded the HTTP call as `test-1.yaml` and the Redis `SETEX` mock as `mock-0` in `mocks.yaml`.
- **Request 2:** Gin handled `POST /user/verifyOTP` and executed Redis `GET devrel@keploy.io`. Keploy recorded the verification test as `test-2.yaml` and the Redis `GET` mock as `mock-1` in `mocks.yaml`.

Now stop the recording process in your first terminal by pressing `Ctrl + C`. Keploy will gracefully shut down and write all test specifications and wire mocks to disk.

</Step>

<h2 id="ci-cd-integration">Integrating Keploy into CI/CD (GitHub Actions)</h2>

Because Keploy mocks all downstream databases hermetically, your CI pipeline no longer needs `services: redis` or database migrations. Tests run fast, offline, and reproducibly.

Here is a ready-to-use GitHub Actions workflow file:

<CodeBlock language="yaml" filename=".github/workflows/keploy.yml">
{`name: Keploy Regression Tests

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.22'
          cache: true

      - name: Install Keploy CLI
        run: |
          curl --silent --location "https://github.com/keploy/keploy/releases/latest/download/keploy_linux_amd64.tar.gz" | tar xz -C /tmp
          sudo mv /tmp/keploy /usr/local/bin/keploy

      # Notice: No Redis service container needed!
      - name: Run Hermetic Keploy Tests
        run: |
          sudo -E keploy test -c "go run main.go" --delay 10 --generate-coverage`}
</CodeBlock>

<h2 id="key-takeaways">Key Takeaways & Comparison</h2>

| Feature | Traditional Unit Testing | End-to-End Testing | Keploy |
| :--- | :--- | :--- | :--- |
| **Code Changes** | High (interfaces, dependency injection) | Low | **Zero (works on unmodified binaries)** |
| **Mocking Effort** | Manual (`gomock`, stubs) | None (uses real DB) | **Automatic (captures network bytes)** |
| **Execution Speed** | Fast (<1s) | Slow (minutes) | **Fast (runs in seconds)** |
| **Flakiness** | Low | High (network drops, state drift) | **Deterministic (idempotent YAML)** |
| **Coverage Accuracy**| Synthetic / Mock assumptions | Real production flows | **Real traffic captured accurately** |
