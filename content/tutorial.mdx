Keploy records real traffic and the Redis calls, then replays them as tests and mocks without code changes.

In this tutorial, I'll walk you through testing a Go Gin authentication service that depends on Redis for OTP (One-Time Password) verification. I'll show you how I ran the Keploy Docker flow on macOS, recorded real traffic, handled dynamic tokens, and ran offline test suites.

## Gotchas I hit

- **Apple Silicon Docker Desktop eBPF Virtualization:** Container-to-container packets over user bridge networks don't traverse standard host sockets, so the Keploy container couldn't capture traffic from a `curl` on the macOS host natively. The solution was the containerized Docker flow.
- **Go 1.23 Docker Toolchain Mismatch:** I had to update the sample `Dockerfile` from `golang:1.20-alpine` to `golang:1.23-alpine` because `go.mod` required `go1.23.0`.
- **Docker Image Version Pinning:** Without a tag, `ghcr.io/keploy/keploy` pulls a `v3` image where the entrypoint is different. Pinning to `:v2.4.0` fixed it.
- **The Redis host:** In the Docker flow, the Redis host in `helpers/redis/redisConnect.go` changes to `myredis:6379`.
- **Dynamic Token Noise:** The verify API generates a JWT signed token on every run, failing the test. Adding `body.token` to the noise section in the test YAML made it pass.

<StepGroup>

<Step title="Clone the Sample App & Update Dockerfile">

First, I cloned the Keploy Go samples and navigated to the `gin-redis` project.

```bash title="Terminal"
git clone https://github.com/keploy/samples-go.git
cd samples-go/gin-redis
```

Since I was using the Docker flow, I opened `helpers/redis/redisConnect.go` and changed the Redis host to `myredis:6379`. I also updated the `Dockerfile` to use `golang:1.23-alpine` to match `go.mod`.

Then, I built the Docker image:

```bash title="Terminal"
docker build -t gin-app:1.0 .
```

</Step>

<Step title="Start Redis on a Custom Network">

Keploy and the application need to be on the same Docker network to communicate. I created a network and started Redis.

```bash title="Terminal"
docker network create keploy-net
docker run -d --name myredis --network keploy-net redis:latest
```

</Step>

<Step title="Record API Traffic">

I used the official Keploy Docker container, pinned to version `v2.4.0`. Setting up an alias makes the CLI commands easier to run.

```bash title="Terminal"
alias keploy="sudo docker run --name keploy-v2 -p 16789:16789 --privileged --pid=host -it -v $(pwd):/app -v /sys/fs/bpf:/sys/fs/bpf -v /sys/kernel/debug:/sys/kernel/debug -v /var/run/docker.sock:/var/run/docker.sock -v /etc/docker/certs.d:/etc/docker/certs.d --rm ghcr.io/keploy/keploy:v2.4.0"
```

Then, I started Keploy in record mode. Keploy automatically intercepted the network calls.

```bash title="Terminal"
keploy record -c "docker run -p 3001:3001 --rm --network keploy-net --name ginRedisApp gin-app:1.0"
```

<Callout type="info" title="Native Alternative">
If you are on native Linux, you can skip the Docker network and use `go build -o gin-redis` followed by `sudo -E keploy record -c "./gin-redis"`.
</Callout>

In another terminal, I made the API requests:

```bash title="Terminal"
$ curl --location 'localhost:3001/api/getVerificationCode?email=something@gmail.com&username=arnav'
{"status":"true","message":"OTP Generated successfully","otp":"9167"}

$ curl --location 'localhost:3001/api/verifyCode' --header 'Content-Type: application/json' --data-raw '{"otp":9167,"email":"something@gmail.com"}'
{"status":"true","token":"eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...","username":"arnav","message":"OTP authenticated successfully"}
```

Once I stopped the app (Ctrl+C), Keploy generated the test and mock YAML files.

</Step>

<Step title="First test run fails, and why">

Next, I ran the tests. I could even stop the Redis container (`docker stop myredis`) and Keploy would seamlessly mock the Redis calls offline.

```bash title="Terminal"
keploy test -c "docker run -p 3001:3001 --rm --network keploy-net --name ginRedisApp gin-app:1.0" --delay 10
```

However, the second test failed:

```bash title="Test Output (Failed)"
--------------------------------------------------------------------
Testrun: test-set-0 | Testcase: test-1 (GET /api/getVerificationCode)
Result: PASSED ✅
Status Code: 200 OK
--------------------------------------------------------------------
Testrun: test-set-0 | Testcase: test-2 (POST /api/verifyCode)
Result: FAILED ❌
Status Code: 200 OK
Diff:
    body.token:
        expected: "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ2YWx1ZSI6ImdtYWlsLmNvbSIsImV4cCI6MTc5MDYxNjUyMX0.S2tX6pQB0_Jg1TTNn6321GpeSv1M5q064QuFD8jWbkk"
        actual:   "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ2YWx1ZSI6ImdtYWlsLmNvbSIsImV4cCI6MTc5MDYxNjg5MH0.F9vKL2_p9x18QpZbX_8Nkmv31JmPqz89Lq01Nzk3OPQ"
--------------------------------------------------------------------
```

The failure is because `/api/verifyCode` generates a randomly signed JWT session token on every run. To fix this, I simply added `body.token` to the noise section in `test-2.yaml` to ignore it during assertions:

```yaml title="keploy/tests/test-set-0/test-2.yaml"
  assertions:
    noise:
      - header.Date
      - body.token
```

Now, re-running the test succeeded:

```bash title="Test Output (Passed)"

Status Code: 200 OK
--------------------------------------------------------------------
```

<Step title="CI/GitHub Actions Integration">

To automate this pipeline, you can use the Keploy GitHub Action. It relies on the tests and mocks we generated earlier.

```yaml title=".github/workflows/keploy.yml"
name: Keploy API Tests
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.23'
          
      - name: Build Application
        run: go build -o gin-redis
        
      - name: Run Keploy Tests
        uses: keploy/test-action@v1.0.0
        with:
          command: ./gin-redis
          delay: 10
```

</Step>
